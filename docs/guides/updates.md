# 更新机制

dsh-piggy 桌面版由两层组成，因此更新方式也分两种。

## 游戏包

根目录 `package.json` 的版本号是游戏版本，例如 `0.26.0`。规则、界面、立绘和大多数功能都在游戏包里。桌面版可以从 Release 下载压缩包，校验 SHA-256 后切换，不需要替换 EXE。切换前会备份存档，并保留上一个游戏包用于回退。

下载、校验和解包在准备阶段完成，现用游戏可以继续运行。准备成功后才关闭游戏写者，确认存档成功并备份最终状态，再切换版本和重启；准备阶段退出会取消下载。

回退只允许切换到能读取当前存档版本的游戏。升级导致存档格式提高后，不能直接回退到只支持旧格式的版本；不兼容的回退会被拒绝，不修改当前激活版本。

旧外壳下载的游戏若没有存档兼容记录，会从该版本已有源码中的 `STATE_VERSION` 数字常量补齐记录，再检查是否可以回退，无需重新下载。无法识别兼容信息时，更新页会提示从版本列表重新安装该版本。

DSH 插件不能安全地重写用户本地仓库，所以它只读发布页列表、选中版本时再向 npm 核对这一版是否已发布，最后给出版本安装命令和发布页链接，由用户自己在 DSH 里按版本安装（见下面「DSH 插件：查看版本和手动安装」）。用户仍通过 DSH 命令或本地源码更新。

## DSH 插件：查看版本和手动安装

DSH 插件形态的「设置 → 更新」会读 `channel.js` 选定的发布页列表：GitHub 渠道读 GitHub Releases，Gitee 渠道读 Gitee Releases。列表只收游戏版本，草稿和 `ext-<key>-<版本>` 扩展发行版会被过滤掉。

这条链路**不自动跟版**：列表来自发布页，不是 npm 的 dist-tags；DSH 不会后台升级插件，也不会因为 npm 上的 `latest` 变了就换掉你现在用的版本。装哪一版、什么时候换，都由你在自己的 DSH 里执行命令决定，页面只给命令和发布页入口。

- 正式版直接列出；点一个版本展开更新说明和发布页按钮。
- 测试版收在「测试版 N 个」下面，默认折叠，点开才能选；测试版不弹气泡、不亮红点。
- **发布页上有标签不等于 npm 上已经有这一版。** npm 包由发布流程按标签单独发布（OIDC 可信发布，见 `.github/workflows/npm-publish.yml`），标签和 npm 之间有时间差（例如 v0.37.1 的标签和发布页都在，npm 上当时没有这个版本）。所以只有用户选中、展开某一版时，更新页才去问 npm 的精确版本元数据：

  ```
  https://registry.npmjs.org/dsh-piggy/<版本>
  ```

  这是精确版本接口，只回答这一版在不在，不会拉整包的版本表；打开版本列表时不会批量查询，200 和 404 的答案按版本记住，收起再展开不重复问。

  - **200（npm 上有这一版）**：显示按版本的安装指引

    ```sh
    dsh plugin --profile web add dsh-piggy@<版本>
    ```

    版本号用发布页上的完整版本号（RC 要带 `-rc.N`，不能只写 `0.37.2`）。例如 npm 上已有这一版时：

    ```sh
    dsh plugin --profile web add dsh-piggy@0.37.2-rc.3
    ```

    用别的 profile 时把 `web` 换成自己的。装完重启 DSH，再刷新页面；更新页顶部的「现在 v…」应该变成新版本。不带版本号的 `dsh plugin --profile web add dsh-piggy` 装的是 npm 的 `latest`（正式版），不会拿预览版。
  - **404（这一版没发到 npm）**：说明这一版只发在发布页上、没有对应的 npm 包，并给发布页入口；不显示一条 npm 上根本装不上的命令。
  - **网络失败或其它状态码**：显示「没能确认 npm 上有没有这一版」，给「再查一次 npm」按钮；这只是没问到，不代表这一版不存在。
- 选中比现在在用的更旧的版本时，会先提示导出存档，并说明旧版本可能读不了现在的存档；更新页只给安装命令，不会自己执行降级。
- 「刷新」会重新问发布页，同时清掉记住的 npm 答案；问不到发布页时显示原因和「再试一次」，刷新失败会保留上一次的列表；发布页没有可安装版本时给出发布页入口。DSH 不会自动替换插件文件。

## 桌面外壳

`apps/desktop/package.json` 的版本号是外壳版本，例如 `0.3.0`。外壳负责 Electron、窗口、托盘、预加载桥和本地更新器。Windows EXE、Linux AppImage 和 macOS App 都属于这一层。

游戏包负责布局、可点区域和桌面样式，外壳负责实际窗口操作、光标命中采样及系统接入（见开发文档「桌面程序和游戏包怎么分工」）。游戏包内的布局修复可以热更新；外壳的线程、文件服务或系统接入修复需要更新安装包。

「设置 → 更新」会分别显示**游戏版本**和**桌面外壳版本**。版本按正式版分组，点开一组看更新说明和按钮；测试版收在对应正式版下面、默认折叠，只能手动安装，组标题上标「测试版 N」，更新页顶部也会提示列表里有几个测试版。只有测试版的版本组会在展开后直接列出测试版，方便找 RC。红点和「更新到最新」只看正式版；测试版不会弹气泡、不会亮红点，想试才自己点开安装。游戏版本升级沿用下载、校验、备份存档和回退；外壳版本升级负责窗口、托盘等系统功能。测试版的游戏条目还会显示配套外壳版本，并给出「下载配套桌面版」入口：只换游戏包不会更新窗口功能，换了游戏包但外壳较旧时仍然可以补装。从外壳 v0.2.0 起，支持以下方式：

| 安装方式 | 外壳更新 |
| --- | --- |
| Windows 安装版（setup.exe） | 在更新 App 下载，完成后点击“重启并安装” |
| Linux AppImage | 在更新 App 下载，完成后点击“重启并安装”；AppImage 所在目录需可写 |
| Windows 便携版（portable.exe） | 更新 App 说明原因并打开发布页；下载后替换旧 EXE |
| macOS 未签名 DMG | 更新 App 说明尚未签名并打开发布页；下载后替换应用 |

支持应用内更新的外壳下载完整安装包，不使用差分下载，以避免主线程处理差分数据。下载流量相应增加，完整性校验和 Windows 发布者签名判断保留。

此前发布的外壳 v0.1.x 没有安装器更新功能，仍需**手动覆盖安装一次**带新更新器的版本。此后支持的安装方式才能在 App 内升级外壳。存档位于系统应用数据目录，不在可执行文件中，正常覆盖不会清空猪。

Release 的游戏清单包含两个外壳字段：

- `minShell`：运行该游戏包所需的最低外壳版本，低于它时禁止热更新。
- `shellVersion`：发布该游戏包时推荐的外壳版本。更新页只在「新版游戏需要更高外壳」时醒目提示，否则只显示一行可选更新；测试版在版本列表中默认折叠，用户可手动展开查看。

发版时，外壳有改动就先提高 `apps/desktop/package.json` 的版本，再和游戏包一起打包。Windows 安装版的 `latest.yml`、Linux AppImage 的 `latest-linux.yml` 必须和对应安装包上传到**同一个游戏版本标签**的 GitHub Release；更新器用这些清单核验安装包。游戏包没有外壳改动时，外壳版本号保持不变。
