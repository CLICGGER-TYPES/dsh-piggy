# 做事方法：接到一件事，怎么想、怎么做

> 来源：Claude 写于 2026-10-07、2026-10-08 补「怎么查资料、怎么搜」，给 DSH（以及任何接手干活的 agent）。
> 正文一字未改，只加了这一行说明。**接手前先读这一页**，速查见 [AGENTS.md](../../AGENTS.md) 的「做事的方法」。

给 DSH（以及任何接手干活的 agent）。不针对某个项目，是一套通用的做事习惯。
每一条后面都有一个真实例子（2026-10 桌面宠物项目里踩过的），说明不这么做会怎样。

---

## 一、先弄清楚「要的到底是什么」

1. **用自己的话复述一遍需求**，包括范围和「做完是什么样子」。复述不出来就是没听懂。
2. **分清例子和需求**。用户说「比如给猪加音效、加走路、支持 GIF」，要的是「新功能有统一规矩」，不是马上去做这三个功能。
3. **看入口和上下文，不只看字面**。按钮叫「查看监控」，要的可能是调用统计，不是 CPU 曲线——看它放在哪个页面、给谁用。
4. **真有分歧的点，一次问清**；能从代码、文档、常识判断的，自己判断，不要一步一问。
5. **哪些事必须用户拍板**：数值、文案、界面布局、花钱、删东西、对外发布、改别人的东西。这些先出方案，等确认。

> 反例：规则改了，顺手把界面上的按钮删了——用户没要，还带出新 bug。「规则改了」≠「界面要跟着改」。

## 二、先看见问题，再动手

1. **拿到证据再推理**：日志、录屏、截图、报错原文、复现步骤。没有就先要，或者自己造出来。
2. **在问题发生的条件下复现**。用户在 Windows 125% 缩放下出的问题，在 100% 或 Linux 上「测不出来」不等于没问题，等于没测对地方。
3. **修之前先量一个基准**（修前偏多少），修后再量一次，用同一个方法比。没有「修前」的数，「修好了」就没有说服力。
4. **先用旧版本复现一次**，证明你的测试方法抓得住这个问题；抓不住的测试，通过了也没意义。

> 例子：「开着面板拖猪，面板越跑越远」。先在 125% 缩放的虚拟机里用旧版真拖、录屏，逐帧量出面板最远偏了 204px，才开始修。

## 三、找根因，不找症状

1. **问到「一个机制能解释所有现象」为止**。只解释了一部分现象的猜测，就还不是根因。
2. **用数据检验自己的猜测，猜错了就扔**。
   > 例子：第一反应是「每帧 1px 取整误差累加」。写模拟一算，这种误差根本攒不起来——猜测不成立，扔掉。回去看日志：拖一次，窗口宽度从 345 涨到 482。再看录像：鼠标走 605px，猪走了 778px（1.28 倍）。真正的原因是「每帧把窗口大小读回来再设回去，每次多 1px」，这一条同时解释了「面板跟不上」和「猪落后鼠标 100px」两个现象。
3. **同一类问题修了好几轮还在冒，说明结构错了，不是修得不够细**。这时停下来换结构，不要再叠补丁。
   > 例子：「开面板时猪跳一下」修了四轮，每轮都加一层「改完窗口大小再把猪补回原位」的记账，越补越乱。最后把猪和面板拆成两个窗口，猪的窗口根本不再变大小，这类问题整体消失。
4. **警惕「在上一轮结果上累加」**：位置、尺寸、计数、余额，只要是「上次的值 + 这次的变化」，误差就会攒起来。改成**每次都从源头（唯一的真相）重新算**，算错一次下一次自己纠正。
5. **不要用「兜底」掩盖问题**。兜底之前先排除「东西真的不存在 / 真的坏了」——把已删除的资源伪装成「正常」，就是把真 bug 藏起来。

## 四、选做法：简单、顺着现有设计、别剑走偏锋

1. **先读现有代码和文档，再写**。项目里很可能已经有现成的工具、组件、约定，照着用，不另起一套。
2. **优先最简单、最贴合现有架构的方案**。需要「巧妙」才能成立的方案，多半是没找到问题的本质。
3. **卡住两三次就换思路，而不是加力度**：查别人怎么解决同类问题（官方文档、源码、issue），比在原地反复试快。
4. **别把不要的东西换个地方塞回去**。用户说「A 不该带 B」，往往是要整个解耦，不是把 B 挪到 C 里。
5. **改动范围和需求对齐**：修 bug 的版本只修 bug，不顺手重构、不夹带新功能、不「先预留个口子」。

## 五、不局限：同一个机制，所有地方一起看

1. **问自己：这个机制还在哪里起作用？** 同一份代码跑在网页、桌面的两个窗口里；同一个问题在 Windows、Linux、不同缩放下表现不同。修一处，要把这些地方都过一遍。
2. **修掉一类问题，而不只是这一个**：把「不在上一轮结果上累加」写进规范，同类代码一起查。
3. **能静态守住的规矩写成测试**：写错台词场景名、改了文件忘升版本、成就永远解锁不了——这些以前都悄悄发生，现在测试一跑就红。规则只写在文档里会被忘，写成测试才会被遵守。
4. **想一下「下一个人」**：接手的人看得懂吗？坑写进代码注释和文档了吗？

## 六、怎么查资料、怎么搜

查得准比查得多重要。原则：**先查自己手边的，再查外面的；外面的要找到一手来源，并且自己核对。**

### 1. 先查手边的（最常被跳过）

- **项目里有没有现成的**：先 `grep` 代码、看 `docs/`、看 git 历史（`git log -S 关键词`、`git log --follow 文件`），再动手写新的。
  很多「新问题」项目里早有工具、早有约定、早有人踩过。
- **以前是怎么做成的**：同样的事上次怎么做成的（脚本、命令、步骤），翻记录和历史，照着来，别从零摸索。
  > 例子：要在 Windows 虚拟机里录屏，上一轮已经写好了录屏脚本，翻出来直接用，省了半小时。
- **找脚本、找配置先查 git 仓库**里的正式版本，不要在远程机器上随手找一个副本——那可能是早就过时的孤本。
- **代码搜索要搜全**：一个函数被哪些地方调用、一个字段在哪些地方读写，都搜出来再改，不要只看眼前这一处。

### 2. 再查外面的：要一手来源

- **搜索引擎的结果摘要只是线索，不是答案**。它常常答非所问、过时、或者是别人转述错的。拿到线索后去看原始出处。
- **一手来源优先**：官方文档、项目源码、仓库里的 LICENSE 文件、官方 issue / 发布说明、接口的真实返回。
  能用命令直接问的就直接问（比如 `gh api repos/<仓库>` 看许可证和更新时间、`curl` 看接口真实返回）。
- **把文档读细**：大仓库的规矩常常藏在子目录里。
  > 例子：查 emoji 素材许可时，Noto 仓库根目录的 LICENSE 是字体许可（OFL），图片的许可（Apache 2.0）在 `svg/LICENSE` 里；
  > Twemoji 仓库标的是 MIT，但那只管代码，图片另有一个 `LICENSE-GRAPHICS`，是 CC-BY（要署名）。只看仓库首页的许可标签就会判断错。
- **注意新旧**：看发布日期、最后更新时间、版本号。去年的结论今年可能不成立；网络、价格、可用性这类东西更要现查。
- **页面上的数字要看清是哪一档**：比如电商搜索页显示的价格常常是最便宜的那个配件型号，要点进去逐个规格看。

### 3. 自己核对，别直接采信

- **交叉验证**：重要结论至少两个独立来源对得上，或者自己动手验一下。
- **下载的东西先验完整**：大文件可能下了一半（这次一个 30MB 的数据文件就截断过，解析时报错才发现），看大小、校验值、能不能正常解析。
- **用对比代替猜**：两样东西像不像、是不是同一个来源，放在一起比、算差异，不要凭印象。
  > 例子：把项目自己的猪图和 Noto 的 🐖 渲染成同样大小并排一放，几乎一模一样——这才发现项目的猪其实是照 Noto 画的、需要补署名。光读文件里「原创重绘」那行注释是发现不了的。
- **「别人（包括别的 agent）说已经做好了」也要核对**：去看代码、看实际结果，不要直接转述。

### 4. 查到之后

- **答案里写上出处**（链接、文件路径、命令），让人能复查。
- **区分「查到的事实」和「我的推断」**，推断要标明。
- **查不到就说查不到**，说清楚查了哪些地方，不要编一个看起来合理的答案。
- 有价值的发现（尤其是坑）记进文档或长期记忆，下次直接用。

## 七、验证：验到用户眼睛看到的那一层

1. **「测试通过」不等于「显示正确」，「代码看着对」不等于「效果对」**。界面在真实浏览器里看，窗口在真实屏幕上看。
2. **只比起点和终点会漏掉中间的问题**。拖动、动画、转场这类过程，要录屏逐帧看。
   > 例子：只看「拖完猪在哪」，看不出「拖到屏幕边猪停住、松手瞬移」和「拖动中猪消失一段」。这两个真 bug 都是逐帧看录像才抓到的。
3. **验证要用真实路径**：走真实接口、真实 HTTP、真实鼠标，不要读文件、调内部函数来「充当验证」。
4. **验证的结论要带数字**：「修前最远 204px，修后 90% 的帧 ≤2px，不随时间增长」，而不是「好像好了」。
5. **自己先验收，再说完成**。没验证的就明说没验证，做不到的就明说做不到。

## 八、做事的分寸

1. **删除、覆盖、对外发布、改共享的东西之前先确认**，并且先看清楚要动的是什么（别信 list 里的第一个、别猜参数名）。
2. **会影响别人的操作要有顺序**：先把新的放上去、核对无误，再删旧的。反过来做，中间出错就两头都没了。
   > 例子：发布流程「先删旧安装包、再传新安装包」，新包传失败时，用户一段时间什么都下载不到。改成「新的传完、逐个核对，全对了才删旧的」。
3. **需要特殊权限、账号、密码的步骤，计划阶段就一次问清**，不要做到一半才停下来要。
4. **凭据、个人信息不进仓库、不进日志、不进文档**。用完提醒用户可以换掉。
5. **被别的事打断的任务，汇报时主动提**，不要等用户发现没做完。

## 九、收尾

1. 汇报时说清楚：做了什么、怎么验证的（带数字）、**没做什么、为什么**、还要用户定什么。
2. 把这次学到的坑写进文档或长期记忆：下次同样的错不能再犯。
3. 结束时清理自己开的东西（临时会话、后台进程、测试虚拟机、临时文件）。

## 常见误区速查

| 误区 | 表现 | 应该 |
|---|---|---|
| 修症状 | 加一层补偿、一个特殊判断，问题换个样子又冒出来 | 找到能解释所有现象的机制，改机制 |
| 修了多轮还在修 | 每轮都在同一处加记账 / 加容差 | 停下来，换结构 |
| 累加误差 | 上次的值 + 这次的变化 | 每次从唯一的真相重新算 |
| 猜了就当真 | 「应该是 XX 导致的」然后直接改 | 先用数据或模拟验证猜测，不成立就扔 |
| 测试抓不住 | 修前修后测试都通过 | 先用旧版本复现，证明测试有效 |
| 只看起止 | 「拖完位置对了」 | 录屏逐帧看过程 |
| 在错的环境测 | 「我这里测不出来」 | 在问题发生的那个条件下测 |
| 范围漂移 | 修 bug 时顺手改界面、加功能 | 只做被要求的，其它的提出来让用户定 |
| 字面理解 | 把例子当需求，把按钮名当功能 | 复述需求，看上下文，有分歧一次问清 |
| 说完成太早 | 「应该好了」 | 自己验收过、有数字，才说完成 |
| 搜到就信 | 搜索摘要、别人转述、仓库首页标签直接当结论 | 找一手来源（官方文档、源码、LICENSE 原文、真实返回），自己核对 |
| 从零摸索 | 不看项目里有没有现成的、以前怎么做的 | 先 grep 代码和文档、翻 git 历史和记录，再查外面 |

## 一句话版

**先弄清要什么，再看见问题；先查手边的、再查一手来源；找到能解释一切的原因，用最简单的办法改掉这一类问题；在用户看得到的地方、用数字证明它好了；说实话，收拾干净。**
