# 外部桌宠模式

> 状态：公开预览版 **0.37.2-rc.5**（配套桌面外壳 0.6.8-rc.3）已在 [GitHub](https://github.com/CLICGGER-TYPES/dsh-piggy/releases/tag/v0.37.2-rc.5) 和 [Gitee](https://gitee.com/clicgger/dsh-piggy/releases/tag/v0.37.2-rc.5) 发布，npm 的 `rc` 通道也已提供该版本。本文只描述这个公开版本的实现；字段和事务细节见[外部桌宠合并规则](../design/external-merge-rules.md)，接入其他 agent 见[接入指南](agent-adapters.md)。

默认仍然是 DSH 内嵌猪和桌面猪各养一只。外部桌宠是可选连接，不会在后台自动合并两份存档；只有用户在 DSH 中明确选择「把内嵌猪合并到桌面猪」并完成预览、确认后，才会执行一次性合并。

## 打开联动

桌面版设置里的「外部连接 → 允许本机的 DSH 联动」默认关闭。打开后，桌面在本机启动独立的配对接口和工作接口；DSH 设置里的「外部桌宠」可以重新检测并连接。浏览器不会收到接口令牌。

两个接口都只监听 `127.0.0.1`，各自使用独立令牌，并拒绝带跨站来源的请求。这是同一台电脑上的本机联动，不是公网、局域网或跨设备连接功能。

## 只把工作和面板交给桌面猪

这条路径不合并资产：

- DSH 内嵌猪进入暂存；暂存期间不饿、不病、不长大。
- DSH 面板操作转给桌面猪，工作事件只投递一次到桌面目标。
- 桌面断开时保留外部模式和工作队列，不自动回退成另一只猪。
- 切回内嵌后，从暂存时间接着养；暂存期间没有被按墙钟补算。

## 把内嵌猪合并到桌面猪

合并只在用户从 DSH 明确发起时进行。完整字段和冲突规则见[外部桌宠合并规则](../design/external-merge-rules.md)。

### 1. 预检与活动处理

- 两边存档都必须能迁移到当前 v15；至少有一只是活着且已孵化的小猪。
- 进行中的打工、上课、旅行、番茄钟、手动或自动钓鱼先逐项列出。用户可以去对应一端处理，也可以对支持的瞬态选择强制终结；强制终结的退款、鱼饵和次数后果按当时实际状态显示。
- 两边状态读不出来、任一边存档版本高于当前实现，或内嵌端合并规则版本高于桌面端时，不进入合并。

### 2. 预览

预览会给出资产相加和进度取高后的结果，并让用户逐组选择身份：

- 名字。
- 样子：形态、皮肤、穿戴。
- 性格：性格、口头禅、签名、生日。
- 偏好：称呼、免打扰、离线喂食、时间倍率、钓点。

每组可以跟桌面猪、跟内嵌猪，或在桌面端给出候选时自己改。新名字沿用当前游戏的 5 字上限；选择已有的一边时，旧存档里的长名字原样保留，不截断。

两边都有数据、但桌面端没有对应合并钩子的扩展，逐个二选一，默认桌面猪。装有官方合并钩子的扩展先调用钩子；钩子异常、返回非法数据或留下未解决冲突时，降级为同样的二选一，不会用半成品数据覆盖。

如果检测到两只猪可能是同一份存档的副本（相同 seed 和相近出生时间，或名字、经验、金币、徽章高度重合），预览会明确提示。提交前必须选择「只保留桌面猪」「只保留内嵌猪」或「仍然合并」；前两项不做任何资产相加。

预览阶段桌面端只读取和计算，不改目标存档；DSH 侧会冻结源端并生成预览用归档。预览 10 分钟过期。同一时间只保留一个预览，新预览会替换旧预览；取消或过期时恢复源端暂存状态，若发起前就处于「只连接」的暂存模式，则恢复到该模式。

### 3. 提交与原生确认

提交时 DSH 会重新校验预览令牌、源归档哈希、桌面运行时和预览后的状态变化。桌面端弹出原生确认框，显示桌宠、内嵌猪和合并后的摘要；**60 秒内没有确认按拒绝处理**，默认按钮是取消。DSH 的提交请求最多等待 90 秒，覆盖这段原生确认时间。

确认后，桌面端在写入前生成并重新解压校验一份目标存档完整备份；DSH 侧在预览时已经生成并校验源端完整备份。只有备份成功才继续。

### 4. 结果未知时只查询原事务

如果 DSH 没收到明确结果，不会再次提交、再次相加，而是用同一个 `mergeId` 查询桌面端的原事务状态：

- `committed`：按已提交处理，继续内嵌猪退役。
- `failed`、`rolled-back`：按失败或已撤销处理，立即恢复源端。
- `unknown`：源端保持待恢复，继续用同一 `mergeId` 查询，不重新提交；查询结果变为其他状态后按该状态处理。
- 持续未知超过 2 分钟：恢复源端暂存，保留现场供排查。

桌面端按 `mergeId` 返回已提交结果，因此网络重试不会重复应用同一次合并。

### 5. 退役与撤销

合并成功后，内嵌猪按「写退役标记 → 停内嵌运行时 → 分别幂等改名 state 与 work-events」的顺序退役；改名每一步都可重试，启动时只认原路径，不会把 `merged-*` 当成活动存档打开。退役失败时桌面合并结果保留，DSH 标记为待重试，用户可以重试退役。

最近一次合并可以撤销。撤销先恢复桌面端合并前备份，并备份合并后的桌面进度；再恢复 DSH 源端备份和内嵌猪。只恢复内嵌猪是单独的恢复路径，不撤销桌面端。若桌面端已恢复、DSH 源端恢复失败，界面会明确显示「部分撤销」，保留可继续处理的记录。

合并备份只保留最近一次可撤销所需的一套；清理只碰合并记录里登记过的文件，普通手动导出/导入备份不会被清理。合并记录损坏时，一个旧备份都不删。

## 实现边界

- 配对和工作接口只监听 `127.0.0.1`，令牌独立，拒绝跨站来源。
- 桌面 split 和 stage 共用联动管理器；只有主游戏窗口能打开许可，扩展窗口不能操作此设置。
- DSH 管理路由始终存在，面板路由随内嵌/外部模式互斥切换，避免两套存档同时接收操作。
- 在线扩展合并只调用桌面已安装且声明支持的钩子；异常、非法数据或未解决冲突降级为二选一。
- 在目标存档内，合并事务只写 `state.json`、工作收据和本次涉及的皮肤文件；目标/源端完整备份、`backups/merge-history.json` 合并历史和 `backups/merge-<mergeId>/` 事务记录按流程另外写入。扩展目录、日志和窗口设置不会被改动。
