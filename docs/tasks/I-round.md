# I 批次：桌面版窗口几何重做（根治「更新后偏移 / 拖动异常」）

> 来源：用户 2026-10-06 反馈（v0.32.0 之后）：「经常会碰上更新之后右键桌面版的猪会偏移，拖动异常，上下屏拖动问题……linux 就算了，为什么 windows 下稳定性也这么差？」
> 用户明确要求：**不要再打补丁，换掉底层逻辑**。
> 本卡的根因不是推测：读代码 + 一轮只读审计（含用纯函数复现的模拟数字）。标「待实测」的地方会写明。
> 分工：Claude 写卡 + 实现 + 自测 → 用户实机验收。

---

## 0. 症状与目标

**症状**（用户原话归并）：

1. 更新之后，右键猪（开面板）猪会**偏移**，而且偏了就一直在那儿。
2. 拖动**异常**：不跟手、跳动、和窗口不同步。
3. **上下屏**（垂直叠放的两块显示器）拖动会突然被弹回。
4. Windows 也一样不稳，不只是 Linux。

**目标**（都要能验收，见第 7 节）：

- 开、关面板、切页、冒气泡、换皮肤、更新之后——**猪的屏幕坐标一像素都不动**。
- 拖到哪就是哪：鼠标和猪的相对位置不漂、不弹（跨屏缝也一样）。
- 同一台机器上，**连续开关面板 10 次的位置完全一致**（现在第一次可能是对的，第十次偏了）。
- 更新（游戏包热更新）前后，同一操作的结果一致；版本错配**能被发现并说出来**，而不是悄悄错位。

## 1. 根因（结构性，五条，都有代码证据）

### R1 摆放是「预测一次性发出」，没有任何回读校验 —— 上一版的「量完再修」被删了

2026-10-04 的 `41fd3ca` 把「摆完 → 页面量出猪真实位置 → 主进程再补一次」的反馈回路删掉，改成一次预测到位：
`src/client/desktop/index.js:101-110`（用**缓存**的窗口原点 + **预测**的猪本地框算目标）→ `place.js:66-67` → `main.js:434-447` 照做（2px 死区）。

`anchorCorrection`（`apps/desktop/lib/window-geometry.js:196-225`）**现在只有测试引用，生产代码一次都不调用**（grep 核对）。

**后果**：模型与现实的任何偏差（Windows 取整、缓存过期、夹取、钉边没落准）**不会被修正，而是被下一次计算继承**——这就是「偏了就一直在那儿」。

**为什么当初没测出来**：F10 的验收采的是**渲染端自己算出来的**屏幕坐标（`docs/tasks/F-round.md:177-178`），那正是页面自己的模型，看不见 OS 层面的偏差；而且只在 Linux/Wayland 上测，Windows 明确留了「用户实测」（`F-round.md:149`）。

### R2 页面只有「缓存的窗口原点」这一个真相，它过期就变成真实的猪位移

缓存在 `apps/desktop/preload.cjs:5-42`；同步路径（`place` / `askGeometry`）才刷新，其余靠主进程异步推。

**已核实的漏洞**：面板开着拖完，**不同步几何**——`src/client/desktop/index.js:170` 是 `if (!measure.state.compact) return`，只有收起态才同步。而拖动期间页面故意不 tick（`:124-131`），主进程却以最高 60Hz 挪窗口（`main.js:374-383, 414, 416-422`）。快甩一下就会在缓存里留下几十像素的落差，**下一次内容变化（右键开面板）把它当成真实位移用掉**。

另外 `place.js:62` 的 `resting`（开面板那一刻记下的猪原位）**只算一次，之后不再刷新**（`:75` 只在收起时清）。所以第一次的误差会在面板开着期间的**每一次**内容变化上重复使用。

### R3 持久化状态会被「更新」悄悄作废（这就是「只有更新后才犯」）

- 面板预留范围的 key 里带**实测的猪宽**：`measure.js:158` = `朝向|朝向|Math.round(pigBox.width)`，**key 没有版本、没有迁移**；`validOpenBox`（`:26-34`）的存在本身就说明旧 key 曾经出过事（`603f4bd` 修过一次）。
- 游戏包更新会换掉桌面 CSS / emoji 字体 / 立绘 → 猪的实测宽度可能变 → key 失配 → **收起态不再预留面板** → 那次右键成为「更新后第一次真的改窗口」，R1 的残余就在这一刻显形。
- 更新必然重启 App，而启动是两套位置存储最容易打架的时刻：外壳的 `window.json`（`main.js:141-170, 233-251`）和游戏包的 `localStorage`（`place.js:15, 26-29`）。**现代游戏包下外壳那套是死代码**：`main.js` 的 `lastPigWindow` 只在旧路径 `:354` 赋值 → `window.json` 永远 `pig: undefined`（`:166`）→ 外壳的 `savedPigScreen` 恒为 null。
- 而且 `remember()` 存的是**预测值**（`place.js:91-93` 用 `lastPigWindow`），不是实测值——错的位置会被存下来给下次启动用。

### R4 多屏（尤其上下屏）的夹取逻辑会主动把猪弹走

- 拖动时每帧取「**鼠标所在那块屏**」的工作区（`main.js:377-382`），而 `absoluteDragBounds`（`window-geometry.js:154-173`）要求**整只猪**落在**单块**屏里，禁止跨缝。
  **模拟**（纯函数复现）：上下两块屏（上 y 0–1040、下 y 1080–2120），56px 的猪在下屏 y=1500 开始拖，鼠标移到 y=1070（越过缝 10px）→ 目标 1070 被夹到 984，**10px 的鼠标移动让猪弹了 86px**（另一组参数弹过 516px）。弹回量最多是「猪高 + 任务栏」。
- 散步 / 旧游戏包走 `moveAcrossDisplays`（`:131-141`），夹的是所有屏的**外接矩形**而不是真实并集。**模拟**：上屏 1920 宽、下屏 2560 宽左对齐 → 并集 x 0–2560，允许窗口停在 x=2000，而上屏只到 1920 —— **猪能被走到不属于任何屏幕的地方**。
- `geometry.js:66-76 nearestArea` 按距离挑，平手时按 `getAllDisplays()` 顺序，而这份列表是上次推送时的**快照**，缝附近可能挑错。
- **全项目零处处理 `scaleFactor`/`devicePixelRatio`**（`apps/ src/ test/ scripts/` grep 无命中）；混合 DPI 只靠两个 2px 容忍硬扛。

### R5 版本闸门是摆设，所以「旧外壳 + 新游戏包」既拦不住也看不见

- `apps/desktop/package.json` 的 `piggy.minShell` **从引入起一直是 `0.1.0`**（git log -p 核对，外壳到 0.5.0 都没升），而契约已经到 `DESKTOP_VERSION = 3`（`src/client/desktop/index.js:15`），游戏包的桌面模块实际需要外壳 ≥ 0.3.0。`versions.js:126-127` 只在 `minShell > shellVersion` 时拦——**永远不成立**。
- `loader.js:28` 写进去的 `data-piggy-desktop` **全项目没有任何地方读**（只有 CSS 和一条测试）。
- 而几何逻辑**整个在游戏包里**（可热更新），外壳只负责执行。所以每次「设置 → 更新」之后，你们默认就跑在「新几何 + 旧外壳」的错配状态里，运行时无法察觉。

**另有两条放大器（不改，但要知道）**：透明窗口每次 `setBounds` 都可能闪/叠影（`main.js:191-193, 210-215`，就是 HANDOFF 里那条「抽动 + 一帧叠影」）；窗口 60Hz 移动 vs 页面 30fps 绘制（`main.js:32-33, 261`）。

## 2. 做完之后必须成立的不变量

| | 不变量 | 怎么判定 |
|---|---|---|
| **I1** | 猪的屏幕坐标**只有两个来源**能改：用户拖动（含散步）、用户换体型档/显示器变化时的显式重锚。开合面板、气泡、切页、换皮肤、更新、测量抖动都不许改 | 连续开关面板 10 次，采样猪的屏幕坐标，波动 ≤1px |
| **I2** | 每次摆放 = **读回 → 计算 → 应用 → 验算**；验算超差就修一次（≤2 次 `setBounds`，且只在超差时第二次） | 假 shell 注入 1–2px 的 setBounds 偏差，最终猪的屏幕点仍与目标差 ≤1px |
| **I3** | 磁盘/localStorage 里的位置是**显示器相对坐标 + 布局签名**，带 schema 版本和迁移；显示器变了也能落地 | 旧格式能迁移；拔掉一块屏后猪仍在某块屏上 |
| **I4** | 拖动夹取**允许跨缝**，只在整只猪能被另一块屏装下时才跟随切换 | 上下屏缝上 10px 移动，猪位移 ≤ 鼠标位移 + 4px |
| **I5** | 游戏包启动时**探测外壳能力**，缺能力就明确降级/提示；加基础动作就升 `minShell` | 伪造旧外壳，界面出现「桌面程序版本过旧」提示 |

## 3. 怎么换（设计）

### 3.1 所有权（改完是这样）

| 东西 | 唯一所有者 | 说明 |
|---|---|---|
| 猪的**屏幕坐标** | 游戏包（显式状态，I1） | 只有拖动/重锚改它；存显示器相对坐标 |
| **窗口矩形** | 外壳执行、游戏包计算（现状不变） | 但计算**必须用回读值**（I2） |
| **猪在窗口里的本地框** | 游戏包，按**布局签名**缓存 | 签名 = 面板朝向 + 开合 + 体型档 + 猪宽(4px 量化) + scaleFactor |
| 拖动期间的夹取规则 | 主进程，**按下时定一次** | 不再每帧按鼠标所在屏重算 |

### 3.2 闭环（消灭 R1、R2）

- `placement.decide()` 的 `bounds` 入参改成**决策时同步回读**的窗口矩形（`place({})` / `askGeometry()` 已经是同步 IPC，直接可用），不再用 preload 的缓存做决策输入。
- 新增一次**验算**：`place()` 后用「回读窗口 + 实测 `layoutBox(.dp-pig)`」反算猪的屏幕点，与目标比，>1px 就再 `place()` 一次（有界，最多一次；只在这种超差时才会多一次 `setBounds`，不违反 2px 死区的初衷）。
- `resting` 在面板开着期间**每次内容变化都用回读值刷新**，不再是「算一次用到底」。
- `endDrag` **所有情况**都重新标定几何（补上 `desktop/index.js:170` 那个 early return）。

### 3.3 位置状态（消灭 R3）

- 存 `{ displayId, x, y }`（相对该显示器 `workArea` 左上角）；启动时换算绝对坐标；显示器没了 → 最近的屏 + 夹住。
- 面板预留范围 key 改成 `dsh-piggy:desktop-layout:v2:<签名>`，带 schema 版本；旧 key 一次性忽略并按需重建（不迁移内容，避免把坏数据带过来）。
- `remember()` 存**实测**的猪屏幕点，不再存预测值。

### 3.4 拖动夹取（消灭 R4）

- 按下时确定夹取策略：**允许跨缝**——只要猪的框和**某一块**屏的工作区有交集就合法（多矩形夹取，不是单矩形）。
- 只有「整只猪能被另一块屏装下」时才让夹取区域跟随切换，避免边界抖动。
- `moveAcrossDisplays` 改成按**真实显示器矩形集合**夹取，而不是外接矩形，消除死区。

### 3.5 版本闸门（消灭 R5）

- `minShell` 与 `DESKTOP_VERSION` 绑定：加基础动作就一起升。
- 游戏包启动时**能力探测**（`place`、`logs.save`、`setShape`…）：缺关键能力 → 走保守路径 + 设置页显示「桌面程序版本过旧，请更新」。
- 待实测确认后再删旧路径（见阶段 4）。

## 5. 不做 / 做了也没用（写清楚免得来回试）

- **「窗口开成全屏透明、猪用 CSS 在里面挪」**：最彻底，但你们已经试过并否掉了（`HANDOFF §8.2`「透明全屏窗口拖动会卡整机」）。不回头。
- **Windows 分数缩放下 `setBounds`/`getBounds` 差 1px**：Electron/系统的行为，消不掉。闭环能做到「当次修掉、不累积」，做不到「不发生」——这是天花板。
- **让页面直接设窗口绝对位置**：Electron 只有 `setBounds`，跨 DPI 的换算仍在系统手里。绕不过去。

## 9. 同行调研结论（2026-10-06，用户要求「不要自己造轮子」）

调研了 Shimeji-Desktop、eSheep/desktopPet、CppGoose（Desktop Goose 的 Linux 版）、SSP（伺か）、Convai Desktop Pets，以及 Electron 自己的源码注释。

**最重要的一条：架构 A（窗口紧贴精灵 + setBounds）不是错的**——两个活到今天的经典桌宠（Shimeji、eSheep）都用它。我们的漂移更可能是三件具体可修的事，而不是架构选错：

| 来源 | 结论 | 对我们的动作 |
|---|---|---|
| Electron `shell/browser/native_window_views.cc` 注释 | 构造 `BrowserWindow` 时不给 x/y，HWND 会先按主屏 DPI 建在 (0,0) 再挪，副屏上会「缩水」（secondary-creation deflation）；不挪也不该「先建再挪」 | R2：我们本来就把 `...start` 摊进构造参数 ✓，加测试锁住 |
| 同一文件 `OnWidgetBoundsChanged` | `GetWindowBoundsInScreen` 有约 1px 误差，DIP↔像素来回换算丢精度，它自己用 `IsApproximatelyEqual(..., 1)`；把 move/resize 事件回灌 setBounds 会「constant false positives」 | R3：核对容差从 1px 抬到 **2px**（贴着噪声就是来回纠正） |
| Shimeji（Java） | 显示设备**每 5000ms 轮询**一次，因为 AWT 没有可靠的显示器变化事件 | R6：我们订阅了 Electron 的 `display-*` 事件，再加一个 **10 秒兜底对账** |
| eSheep（C#） | 缓存显示器索引在拔屏/RDP 后失效；**每次决策只取一份 `Screen.AllScreens` 快照** | R6：我们每次都用 `getAllDisplays()` 现取、且位置存的是矩形不是索引 ✓ |
| CppGoose（架构 B，每屏一个全屏覆盖窗口） | README「Known limitations」：**分数缩放和混合 DPI 在屏幕边界附近仍会有位置偏差** | **不要为 DPI 迁移到架构 B**（B 不解决这个问题）；B 真正的理由是 Wayland 和多屏简化 |
| Electron PR #10183 / issue #40213 | `setIgnoreMouseEvents(true, {forward:true})` 是**低级鼠标钩子合成的**事件，在 Wacom 数位板下会静默失效，issue 被 closed as `not_planned` | 架构 B 的点击穿透有真实支持负担（用户用笔/数位板时） |
| eSheep `FormPet.CheckFullScreen()` | 前台窗口铺满屏幕时**主动去掉 TopMost**（changelog 里连这个功能的误判 bug 都修过） | R4：待办——全屏游戏/视频时让猪让位。这是 `alwaysOnTop` 的问题，A/B 都有，B 更暴露 |
| SSP（伺か）`seriko.dpi` | 素材**自己声明**作者按什么 DPI 画的（96/120/144/168/192 ↔ 100–200%） | R5：待办——每套立绘带一个 authoredDpi，换算 `display.scaleFactor / (authoredDpi/96)` |
| Shimeji `contains()` 重写 / SSP 文档 | 点击区域**就是**精灵的透明遮罩（Shimeji 逐像素查 alpha；SSP 直接规定透明区不可点），两边都不做每帧命中测试 | R1：我们 Windows 上已经在用「命中区域 + `setHit`」，方向一致 |
| Electron `setBounds` 文档 | macOS 上 y 不能小于托盘高度（20–40px），**低于就会被静默夹住** | 待办：检查 macOS 下的顶部夹取，这可能本身就是一类「偏移」 |
| Electron 文档 | Wayland 下无法用程序移动/定位窗口，`getPosition()` 返回 `[0,0]`，`setAlwaysOnTop` 不支持 | 我们已经强制 `--ozone-platform=x11` ✓ |

**修正一条我自己先前的判断**：我一度认为「全屏覆盖（架构 B）结构上就没有 DPI 问题」——CppGoose 的 README 证明这是错的，B 在分数缩放下同样会在屏幕边界附近偏。B 的正当理由只有 Wayland 和多屏简化，**不是** DPI。

## 10. Windows / macOS 这一轮做了什么（2026-10-06）

用户问「windows呢？」——这里没有 Windows 机器，所以策略是**让 Windows 变得可观测**，同时修掉两个平台专属的坑：

| 做了什么 | 为什么 |
|---|---|
| **`backgroundThrottling: false`** | 这个窗口从不获得焦点（`showInactive` + `skipTaskbar`）。Chromium 默认给后台窗口的 rAF/定时器降频，而页面测量、闭环核对、形状上报**全走 rAF**——被降频就是「挪完窗口猪还慢半拍 / 拖着拖着跟不上」。这是 Windows 上「抽动、一帧叠影」最可能的放大器之一 |
| **启动时把显示器清单写进日志**（id/名称/bounds/workArea/**scaleFactor**/是否内置） | 以前日志里没有这些，Windows 的问题只能靠猜。现在导出的日志第一屏就能看到用户机器是什么配置 |
| **几何里带 `displays`（含每块屏缩放）**，挪窗口/核对日志里加 `display:{id,scale,count}` | Windows 125%/150% 一直在靠 2px 容差硬扛，现在能直接看出「哪块屏、什么缩放、当时差多少」 |
| **macOS：自己先按工作区上沿夹窗口** | Electron 文档写明 `setBounds` 的 y 小于托盘高度（20–40px）会被**静默**夹住。不自己夹的话，模型算的目标永远到不了，闭环核对会一直追一个到不了的目标 |

另外确认过一条**不用改**的：Windows 穿透模式（`setIgnoreMouseEvents(true, { forward: true })`）参数是对的——`forward` 必须有，否则穿透之后页面收不到 mousemove，就再也判断不出鼠标何时回到猪身上（`main.js:223`）。

## 11. 用户真实日志查出来的偏移（2026-10-06 晚）——⚠️ 这一节的修法不对，见第 12 节

用户反馈「桌面版根本没修好」，把 `~/.config/dsh-piggy-desktop/piggy.log` 拿来看，**抓到确凿证据**：

```
drag end  窗口 (1396,501) 304x204
move      请求 → (1376,501,324,656)
bounds place {x:1376, y:501, width:324, height:656}   ← 底边 1157，工作区底边只有 1014
verify    from:{x:1376, y:358, ...}                    ← 回读 358 = 1014−656：系统把窗口顶回工作区
verify correcting dx:20 → 把窗口从 1376 改成 1356      ← 拿被改过的位置算出的假偏差，再挪一次
```

**根因：代码请求了一个系统必然拒绝的窗口矩形。** 窗口比屏幕上剩下的空间还高，系统把它整体上移
143px，而页面不知道——于是猪偏 143px，闭环核对又拿这个被改过的位置算出 20px 假偏差，照它再挪一次，
越修越偏。同一个会话里 6 次修正、2 次「修了还是差」，偏差 20 / 78 / 452px 全是这个链条的产物。

**修法（两条）**：
1. `decide()` 算完窗口矩形后，**无条件夹进该屏工作区**（横竖都夹）——永远不请求一个会被系统拒绝的矩形。
2. 核对用的目标从「意图位置」改成「夹过之后猪真正能落到的位置」（新增 `placement.reachable()`）——
   否则核对会一直去追一个系统不允许的位置，然后一直判自己「还是差」（那两条 `verify still off`）。

**验证**：
- 回归测试：用日志里那一组真实数字（工作区 0,29,1920,985；请求 y=501 高 656）断言底边不超出工作区。
- 复现用户场景（把猪种到屏幕中段 (1400,478) 再开面板）：6 次摆放**全部在工作区内**，
  `place-stale`（请求与回读不符）**0 次**，猪落在 (1396,474)。

## 12. 第 11 节没修好：真正的三个原因（2026-10-06 夜，Claude 接手）——⚠️ 这一节的修法也不够，见第 13 节

| 症状 | 真原因 | 第 11 节为什么没修好 |
|---|---|---|
| 每点一下猪往左跑 20px（日志里 drag start 的 pigScreen 1493→1473…） | setBounds 之后主进程同步回读**立刻**是新尺寸，页面却还没按新尺寸重排。这一拍里 tick 拿「新窗口 + 旧布局」算出一个差 20px 的目标，核对（verify）再照着这个错目标把窗口挪过去 | 第 11 节把核对目标换成 reachable，但 reachable 本身就是这一拍算错的 |

用 `virsh` 连拍也抓不准；最后是**日志的毫秒时间戳**把它钉死的。win11 虚拟机上的原始记录：

```
16:31:02.706  摆放 → x=258 y=392 w=304 h=204      ← 收起态
16:31:02.883  摆放 → x=259 y=390 w=304 h=208
16:31:02.905  摆放 → x=226 y=120 w=324 h=476      ← 面板预留态，向上 272px、高 +272
（随后又回到 204，再回 476 …… 反复）
```

**根因（两条，都在 `src/client/desktop/measure.js` / `index.js`）**

1. **收起朝向每量一次就重新决定 → 自激振荡**。`boxes()` 在收起态调 `fittingOpenBox` 判断「上/下哪个
   放得下」，放不下就把 `state.vertical` 翻过去。朝向决定挂哪块预留区（上下差 272px），一翻窗口就挪；
   挪完猪的屏幕位置变了，「放不放得下」的判断又翻回来 —— 窗口在两个几何之间每 200ms 来回一次。
   这条逻辑当初是为了修「低处一点猪就被拽上去」（见被删掉的那条测试名），但新模型已经有
   「窗口夹进工作区 + 内容反向挪」兜底，不需要靠翻朝向避免出屏。
2. **收起态拖动会把窗口缩成 204 高，松手再长回 476 高**。这是跨进程的两次改动：窗口已经在新位置/尺寸了，
   页面还没重排完，中间一两帧猪就画在错的地方 —— 用户看到的就是「瞬移上去再下来」。

**改法**

- `boxes()` 收起态只按**当前**朝向挂预留区（`validOpenBox`），**不再重新挑朝向**；朝向只在用户动作时改
  （拖动松手走 `collapsedSide()`）。删掉不再有人调用的 `fittingOpenBox`。
- 预留区的 key 对不上时（启动先画占位纸盒、换皮肤改了立绘宽度、更新换素材），**退回到同朝向的任意一条**
  —— 否则第一轮没预留，窗口先缩后长，启动时也会跳一下。
- 拖动期间**不再缩窗口**（去掉 `state.compact` 那条路径），松手就没有那一步 resize。

**验证**

- `node tools/desktop-geometry-check.mjs all` → **ALL OK**，所有场景猪的位置 Δ(0,0)。
- 697 个单测全过（含新增的「测量不许改收起朝向」回归测试）。
- win11 虚拟机实测：修复前启动后窗口在 204↔476 之间反复跳；修复后 `shown` 是 476 → 一次 24px 微调 →
  稳定 476，**静置 18 秒再没有任何摆放**。
- **还没验证**：拖动松手那一下（虚拟机上我的合成鼠标进不到处于穿透状态的应用窗口，需要用户手动拖一次看）。

### 14.1 「偶尔还会」的那一半：松手时重挑收起朝向（2026-10-07 同一晚）

第 14 节修完之后用户反馈「偶尔还会」。在 win11 上再做几轮拖动，日志里抓到剩下的那一次：

```
16:47:32.802  drag end   窗口(184,-288) 324x476
16:47:32.820  → 松手 18ms 后窗口变成 (184,0) 324x632     ← 高度 476 → 632（156px）
16:47:33.557  drag end   窗口(680,8) 324x716
16:47:33.584  → 松手后窗口变成 (680,0) 324x724           ← 8px
```

**根因**：松手时会重挑一次收起朝向（`collapsedSide` → `chooseCollapsedVertical`），一挑就可能换到另一块预留区，
窗口尺寸跟着变（156~272px）。模型会把猪补偿回原位，但**窗口是按新几何先画的、页面晚一拍才重排**，
中间那一两帧猪就画在错的地方 —— 所以是「偶尔」：只有猪被拖到需要换朝向的位置才会触发。

**改法**：松手也**不再**重挑朝向。朝向只在**面板真正打开时**（`sides()`）改 —— 那时窗口本来就在变，
不会多出一帧。删掉没人再调用的 `collapsedSide` / `chooseCollapsedVertical`（连同它们的测试）。

**验证**：`desktop-geometry-check.mjs all` → ALL OK；695 个单测全过。
（虚拟机那次验证没跑成：合成鼠标又进不到处于穿透态的应用窗口，需要用户手动拖一次确认。）

### 14.2 拖动时「抽帧」（2026-10-07 深夜，用户实测）

用户：**拖动猪的时候会抽帧**。代码里是一处明确的取舍冲突：

```js
const FRAME_RATE = 30                  // 整窗合成上限（163c040：Windows 上开整机变卡的取舍）
dragTimer = setInterval(dragTick, 1000 / 60)   // 拖动时窗口按 60Hz setBounds
```

**窗口按 60Hz 移动、整窗合成却卡在 30fps** —— 鼠标在 60Hz 地走，画面 30fps 才更新一次，
猪就「一跳一跳地跟」。虚拟机上还叠了一层：没有 GPU（软件合成），30fps 经常还达不到。

**改法**：只在拖动那几百毫秒里把合成提到 60fps（`FRAME_RATE_DRAGGING`），松手降回 30。
静止时的省电取舍保留。

**待验证**：这台虚拟机没有 GPU，测出来的流畅度不代表真机；需要在有 GPU 的 Windows 上看。

### 14.3 帧率不该由我们写死（2026-10-07 深夜，用户：帧数应该跟显示器同步）

用户指出的对：**帧数该跟显示器同步**，不该写死。查下来是两处都写死了：

| 位置 | 原来 | 现在 |
|---|---|---|
| 窗口合成 | `FRAME_RATE = 30`（`163c040`「修 Windows 上开着猪整机变卡」时定的） | **不设上限，跟显示器刷新率（vsync）**；要压帧率用 `PIGGY_FPS` 兜底 |
| 拖动 tick | `setInterval(dragTick, 1000 / 60)` 写死 60Hz | 读那块屏的 `displayFrequency`，30~240 之间 |

窗口 60Hz 在动、画面 30fps 才更新 → 抽帧；144Hz 屏上反过来又是同一种错配。
另外 `163c040` 真正治住卡顿的是同一次提交里「窗口只框住猪那一小块」，30fps 是捎带的。

顺带加了一条客观证据：松手时写一行 `drag ticks {hz, ticks, maxGap}` —— tick 频率跟不跟得上刷新率，
`maxGap` 一看就知道（远大于 1000/hz 就是主进程被别的活挡住了）。

**待用户在真机确认**（虚拟机没有 GPU，但这台虚拟机上同样有问题，所以按有问题处理，不用它当挡箭牌）。
