# 左轮 4 人桌与联机设计提案 v0

日期：2026-11-18
状态：**提案，未实现**。数值、玩法和界面以用户拍板为准。
关联：`docs/design/roulette-rules-20261118.md`（1v1 AI 规则已定稿并实现）。

## 1. 目标与边界

- AI 4 人桌：1 个真人座位 + 3 个 AI 座位，本地运行，不依赖房间服务。
- 在线 1v1：2 个真人座位，通过现有联机房间中继。
- 在线 4 人：4 个真人座位，同一套 N 座状态机。
- 不在本阶段做：观战、匹配大厅、排行榜、跨房间持久化、账号体系。

## 2. 权威模型

### 2.1 AI 4 人桌

- 权威对局仍在扩展服务端 `extensions/roulette/server.js`。
- 真人座位使用真实金币；3 个 AI 座位共用一个 AI 金库。
- 每个 AI 座位按 `min(stake, vault 余额)` 配注，先到先得；金库不够时少配。
- AI 座位赢下底池时，底池进 AI 金库。

### 2.2 在线对局（提案）

推荐第一版用**房主权威**：

1. 完整对局状态（含子弹位置）存在房主本机的扩展 `extData` 里；扩展 `server.js` 是同步动作，不能自己收网络消息。
2. 房主的扩展大窗口负责房间收发：把客人发来的动作转成 `app.send('remoteAction', ...)`，再把自己的脱敏快照广播出去。
3. 其他玩家只发送动作（装弹、开枪、让枪、下一局）。
4. 房主广播**脱敏快照**，只含 `bulletsLeft`、命数、底池、当前回合，绝不含子弹位置。
5. 真人的金币结算由各自客户端按结果在本地执行；房主不能直接改别人的存档。

这个模型适合朋友局，不做反作弊：

- 房主理论上可以改自己的状态或结果；
- 客人本地结算也可能被改；
- 房主关闭扩展大窗口，对局就停；如需关窗继续，必须做宿主桥接或服务器权威；
- 如果要求真钱级公平，必须把对局和金币账本放到可信服务器，属于另一个阶段。

### 2.3 备选：房间服务器权威

- 房间服务器保存对局状态并结算虚拟筹码；
- 与金币的兑换由各客户端本地完成；
- 需要服务器持久化、身份、反作弊和账本，不建议第一版做。

## 3. 4 人规则提案

以下都是建议值，需用户逐条确认。

| 项 | 建议 |
|---|---|
| 座位 | 4 个；座位顺序随机 |
| 回合 | 当前座位对自己开枪或让枪；之后轮到下一个仍存活的座位 |
| 底注 | 每个座位各付同一底注；真人真钱，AI 从 AI 金库按上限配注 |
| 底池 | 所有座位本局实际配注之和 |
| 命数 | 沿用设置里的 1 条 / 3 条 |
| 淘汰 | 命归零即淘汰，跳过其回合 |
| 胜负 | 只剩一个座位存活时，该座位拿走全部底池 |
| 赛制 | 4 人桌第一版只做单局，不做三局两胜 |
| 让枪 | 付自己底注的 50% 给下一个仍存活的座位，本回合结束 |
| 子弹 | 6 巢；沿用 1v1 的装弹、强制转轮、空枪换手、中弹扣命、子弹打完重装规则 |
| 重装先手 | 随机选择一个仍存活的座位先手 |
| 退出 | 装弹前退出退本局底注；装弹后退出视为认输，底注不退 |
| 断线 | 该座位 20 秒无动作自动让枪；连续 2 次自动让枪后判负 |
| 房主离开 | 结束整局；未装弹退本局底注，已装弹的底池归属待拍板。桌面非持久房会同时关房；独立持久服务器没有房间房主，只结束牌桌对局 |

### 3.1 4 人让枪示例

- A 开枪后轮到 B；B 选择让枪，付 50% 底注给 C（下一个存活座位），回合到 C。
- 如果 C 已淘汰，则顺延到 D，再顺延到 A。
- 让枪方余额/金库不足 50% 时不能选择让枪。

### 3.2 4 人 AI 行为

- 每个 AI 座位独立按当前策略决策；
- AI 不知道子弹位置，只读公开量；
- AI 让枪时同样付钱给下一个存活座位；
- AI 金库不足让枪费时改回开枪。

## 4. 在线 1v1

- 两名真人，规则与现有 1v1 AI 一致；
- 房主权威，客人动作经房间中继发送；
- 双方各自展示自己的真实金币；底注、让枪费、底池结算由各自客户端执行；
- 为降低复杂度，第一版不支持观战和中途换人；
- 断线处理沿用 4 人提案的单座位规则。

## 5. 传输层审计结论（2026-11-18）

现有房间接口**没有**任何通用游戏消息通道，1v1 和 4 人都必须先改宿主。审计依据：

- Node 房间服务只有 `join / state / update / care / care-result / leave` 六条路由（`apps/desktop/lib/room-server.js:323-328`），Rust 版一致（`apps/room-server-rs/src/server.rs:276-282`）。
- `state` 响应固定为 `code/version/hostId + players + careEvents + careResults`，没有游戏字段（`room-server.js:177-188`；`room.rs:834-849`）。
- `update` 只接受 `rev,x,y,facing,emote,targetId`，多一个键直接 400（`room-server.js:280`；`room.rs:440`）；不能用它夹带游戏数据。
- `care` 只认 `feed/bathe/play/medicine`，且目标端主进程会自动执行真实照顾逻辑（`apps/desktop/lib/room-care.js:25`、`main.js:411-428`）；不能当游戏通道。
- `room-client.js` / `room-manager.js` 没有通用 `send`（`room-client.js:118-129`；`room-manager.js:386-396`）。
- 扩展大窗口 `role=ext` 被房间 IPC 拒绝；`piggy:room:update` 只推房间窗口、面板、猪窗口，不推扩展大窗口（`apps/desktop/main.js:449-460`、`ipc/room.js:18-51`）。
- 扩展 `app.send` 只发自己的 `/act`；`server.js` 动作同步、无网络、无异步（`src/client/ext-apps.js:103-138`、`store/ext-actions.js:38-58`）。
- 没有稳定座位/重连身份：`clientId` 每次随机，30 秒无请求移除玩家，token 随之失效（`room-client.js:11`、`room-manager.js:117-155`）。
- 桌面非持久房房主离开会关房；独立持久服务器 `hostId` 为 null（`room-server.js:246`；`room.rs:315`）。牌桌房主必须是游戏级概念。

### 5.1 最小宿主改动（需单独批准）

1. Node + Rust 新增 `POST /v1/room/game`：`seq` 单调、`ext`/`op` 白名单、`data` ≤1536 字节/深度 4/字符串 ≤256 字节；事件队列 16-32 条；`state` 新增 `gameEvents`；`room` 视图新增 `caps:["game"]`。
2. `room-client.js` / `room-manager.js` 新增 `game()`；`publish()` 把 `gameEvents` 抄进 snapshot。
3. `ipc/room.js` 新增 `piggy:room:game`，并授权扩展大窗口发送；`preload.cjs` 暴露窄接口 `room.game`。
4. `main.js` 向扩展大窗口推送轻量游戏事件；`src/client/ext-apps.js` 新增 `app.room`（只含 `status/send/onEvent`，不暴露 token、code、endpoint）。
5. 发送者 `from` 一律由服务端从 token 推导；客户端只接受牌桌房主的快照；客人伪造 `snapshot` 必须被忽略。
6. 断线策略由扩展心跳实现；不做重连。要支持“掉线能回来”，必须再做稳定身份/座位保留，属于更大改动。
7. 不做按接收者过滤的 `state`：MVP 只广播公开字段，子弹数组留在房主 `extData`。若要求“抓包也拿不到子弹”，需要 Node/Rust 都改成按玩家构造 state body，工作量明显更大。

### 5.2 对权威模型的影响

扩展 `server.js` 不能收网络消息，所以“房主客户端跑权威循环、大窗口转发”是唯一的最小实现。大窗口关掉，对局停止。若不能接受，只能选宿主桥接或服务器权威，二者都不是本阶段的最小改动。

## 6. 需要用户拍板

1. 在线对局采用“房主权威、朋友局信任”模型，还是要求服务器权威？（影响工作量和反作弊）
2. 4 人桌第一版是否只做单局？
3. 4 人底注是每个座位各付一份，还是只付一份由赢家通吃？
4. AI 3 个座位共用一个金库，还是各自独立金库？
5. 断线自动让枪 20 秒、连续 2 次判负，是否接受？
6. 房主离开时，已装弹的底池归谁？
7. 4 人桌是否也允许 3 条命和 1-5 发装弹？
8. 在线 1v1 先做，还是 4 人桌先做？
9. 是否批准共享宿主改动：Node + Rust 房间服务器新增 `/v1/room/game`、桌面 IPC 授权扩展大窗口、扩展新增 `app.room`？（不批准就只能先停在本地 AI 对战）
10. MVP 只做公开事件、不做按接收者过滤；同房玩家能看到公开快照，但任何广播都不含子弹位置。是否接受？
11. 房主必须保持扩展大窗口打开，关窗即终止对局；不做重连。是否接受？

## 7. 建议实施顺序

1. 用户确认本提案与第 6 节问题。
2. 单独批准第 5.1 节宿主改动后，先做 Node + Rust 房间通道和桌面桥，按两套服务器各验收一遍。
3. 扩展内在线 1v1：房主客户端权威循环、客人发意图、金币各自本地结算。
4. 扩展内 4 人 N 座 + AI 座位，规则按本提案拍板值。
5. 在线 4 人联调；断线/房主离开/重复动作/伪造快照各测一遍。
6. 独立测试 agent 验收，再谈打包/发布。
