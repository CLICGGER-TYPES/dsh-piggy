# dsh-piggy 现实昼夜、作息与天气系统计划书

状态：设计稿，2026-10-03。依据当前项目 v0.27.1 的代码与 Claude 交接记录编写；本文件不代表功能已实现。

## 1. 目标与设计原则

让同一只猪生活在一套可解释的现实环境中：选定城市决定地理位置和时区；真实日期决定日出日落；天气服务提供当地当前天气；猪根据个人作息、实际睡眠、活动和病情行动。玩家在悬浮猪、主屏、状态、设置、钓鱼和日常记录里应看到一致的结果。

关键原则：

1. 时间、天色、天气、猪的姿态、疾病分别建模，再在展示层合成一句可读的当前状态。生病和睡着可以同时成立。
2. 不增加“精力条”。内部可记录睡眠压力和实际睡眠时长，用于行为和结算；玩家通过姿态与文字理解它。
3. 城市与时区属于安装实例的环境设置，换猪不应重置。作息属于猪，可随领养的新猪重新选择或沿用默认。
4. 猪默认在室内。现实下雨不能无缘无故让室内猪淋湿、生病；天气先提供氛围和活动语境，任何数值影响都必须有明确的暴露场景和可见规则。
5. 缺失或过期的天气数据不得伪装成实时状况，也不得对离线病程补算惩罚。天文昼夜和睡眠在断网时仍能运行。

## 3. 单一环境时钟

### 城市与时区

- 首次进入设置时引导搜索城市，明确展示“城市、行政区、国家、时区”，让玩家选一个结果。不能从 `Asia/Shanghai` 推断玩家住在上海。
- 城市搜索返回地名 ID、坐标和 IANA 时区；选定城市后时区默认跟随城市。提供“跟随设备时区”作为明确选项，但太阳和天气仍取所选城市，界面标明两者不一致；默认不随设备旅行自动改城市。
- 只保存城市 ID、名称、粗略坐标、IANA 时区和用户的时区策略。手动定位可以是可选捷径，必须由玩家触发；不保存连续定位轨迹。
- 所有持久时间戳用 UTC 毫秒；日期、06:00 日界、作息钟点按 IANA 时区解释。夏令时切换时按实际经过的毫秒结算，重复/不存在的本地时刻由一套明确的边界规则处理。
- 时区或城市变更先把旧环境结算到变更时刻，再让新环境从该时刻开始；作息计划从下一个本地睡眠周期生效。签到和其他日限奖励记住上一次实际发放的边界时刻，不能因来回切时区重复领取。
- 普通用户的真实昼夜不受开发模式 `timeScale` 影响。设备时间回拨时不逆向返还衰减、睡眠时长或奖励。

建议的数据契约：`WorldProfile { cityId, cityLabel, latitude, longitude, timeZone, timeZoneMode }` 保存在安装实例配置中；`EnvironmentSnapshot { observedAt, fetchedAt, expiresAt, source, condition, temperature, apparentTemperature, precipitation, cloudCover, windSpeed, sunriseAt, sunsetAt, freshness }` 由服务层给界面；`PigRhythm { preset, asleepSince, wakeWindowUntil, sleepPressure, stageSleepMinutes }` 随猪存档。所有 `...At` 是 UTC 毫秒。客户端显示文字来自宿主快照，不自行套另一套时区规则。天气快照只有“当前展示”的效力；如果将来用于某次活动的结算，活动开始时保存该次活动需要的最小环境字段。

### 天色

- 对选定城市按当地日期获得日出、日落；黎明与黄昏的明暗在边界附近平滑过渡。天色跟太阳走，作息跟猪走：冬日天黑后仍可清醒，夏日天亮后仍可睡。
- 当天文数据暂时不可取时，使用缓存；缓存无效时按坐标和日期做本地天文近似。极昼/极夜地区需要没有日出/日落的正常展示，不套用固定 06:00/18:00。
- 季节仅通过日长与天气体现。先不额外加“冬天更易生病”这类缺少室内温度与保暖机制支撑的处罚。

### 天气

- 候选提供者为 Open-Meteo：城市搜索用 Geocoding API；天气用 Forecast API 的 `current`（天气代码、气温、体感、降水、云量、风速、昼夜标记）和 `daily`（日出、日落），必要时取短时 hourly 数据。天气代码映射成统一内部分类：晴/云/雨/雪/雾/雷等。
- 天气源返回的是模型当前状况，界面写“当地天气”，同时提供“更新于 HH:mm”。服务器侧以约 20–30 分钟缓存、同城请求合并、超时与退避控制流量；面板四秒轮询绝不能触发同频外部请求。
- 请求失败后保留最近有效数据显示“上次天气”，超过约两小时改为“天气暂不可用”；天色、作息、疾病照常运行。天气不直接改变基础饱食/心情/清洁和发病率。
- 离线期间没有可信的逐时天气记录时，历史天气效果按“未知/中性”结算。未来若要让天气影响出行收益，开始活动时需冻结可解释的天气上下文；不能拿重新上线时的一场雨倒填前一晚。
- 宿主侧提供天气读接口或在现有快照中附带缓存结果；外部请求和缓存放在 `store/` 外的服务层，`pet-core/core` 只接收已验证的环境输入。桌面版同一协议路由复用。
- 开发前核对使用方式：Open-Meteo 免费接口仅供非商业用途并要求遵守 CC BY 4.0；界面或“关于”放来源署名。若计划商业化，先换到获准的商业方案或可替换提供者；适配层不能把供应商字段渗进核心存档。

## 4. 猪的作息与状态机

| 预设 | 夜间计划 | 说明 |
|---|---|---|
| 早睡型 | 20:30–06:00 | 早起互动 |
| 规律型，默认 | 21:30–07:00 | 默认体验；23:00 不作为默认入睡时间 |
| 夜猫子 | 23:00–08:30 | 晚间互动 |

三档均为 9.5 小时计划休息，不靠早睡型多发收益。它们是生活习惯，不是强制禁玩时间。猪可处于清醒、犯困、夜间睡眠、补觉、病中休息、外出、死亡等行为状态；饥饿、脏、心情低落、疾病是可以叠加的需求/健康标签。

决策顺序：未孵化/死亡优先；已开始的外出活动按原契约完成；回家后计算病中休息、作息窗口、实际睡眠压力、人工叫醒窗口，得到姿态；再决定闲聊、提示和数值。玩家直接摸猪或照料会叫醒；打开面板、拖动、后台轮询、DSH 工具消息不会反复叫醒。叫醒后可喂食、洗澡、喂药、看医生；夜深且仍困时会再睡，接近自然醒来时保持清醒。重复点击不无限延长同一轮叫醒窗口。

生病时，轻症比预设早约 45 分钟困并可能午睡一次；重症提前约 90 分钟且白天休息更频繁。具体时长是待校准参数。病猪不能因睡姿遮住药物、医生入口。重症活动沿用现有“虚弱限制”，轻症工作仍可作为筹医药费的出路。

## 5. 数值、疾病与天气的闭环

1. 每个实际时间片计算：所在地时刻和天色 → 猪在家/外出 → 醒/睡 → 三条需求衰减 → 发病风险 → 已有病程 → 成长与日常记录。睡眠时长只按实际睡着的片段累计。
2. 睡眠降低夜间消耗，但不回满三条需求、不产生可刷的金币或成长。初始候选为饱食 0.65、心情 0.50、清洁 0.50 倍，仅用于模拟；最终值须由 24 小时测试决定。规律型 9.5 小时从饱食 70 出发，在候选系数下约剩 40；从 50 出发约剩 20，会越过现有饥饿阈值 25，需有睡前提醒与夜间真实风险结算。
3. 病中充分休息可小幅放慢病程并提高 1–3 期的一次性自愈机会；收益以本期实际睡眠累计、基本饱食/清洁条件为前提并设上限。第 4 期的自愈率仍为 0。现有“外出时病程双倍推进”与半薪规则保留作为对照，新增收益必须通过多日模拟验证，不能让睡眠替代治疗。
4. 天气第一阶段影响可观察环境：光线、雨雪等轻量效果、猪的语句和出行页面提示。钓鱼与其他明确的户外活动可在第二阶段加入幅度很小、事前可见的天气修正；室内的学习、休息、看病无天气惩罚。每种活动需要先标记室内/户外/混合，不能按“出门”一词笼统处理。
5. DSH 被动消息、工具调用与现有自动收益需要专项核算：夜间不能因为后台事件让猪不停醒来，也不能借自动喂养制造无限夜间收益。保留原有成长语义时，采用有上限的后台记账与醒后展示，具体方案通过现有事件数据验证。

## 7. 实施顺序与验收

用于对齐产品体验的一天：规律型猪在冬日较早的日落后仍会清醒；20:45 若饱食偏低，状态页提示先喂食；21:00 它犯困；21:30 在家睡下。午夜外面下雨，悬浮场景有轻量雨景，室内睡着的猪不会因此突然变脏或得病。玩家 00:20 叫醒喂药，病情和睡眠状态同时可见，短暂清醒后继续休息。07:00 天已亮时自然醒，签到和礼包提示才浮出来。若整夜断网，天气标为过期，日出、作息与疾病仍按真实时间结算。这个故事需要与三种作息、夏令时和多日离线的自动测试结果一致。

**A. 时间与环境契约。** 定义环境配置、城市时区、UTC 时间戳、06:00 日界和天色的纯函数；增加城市搜索与天气适配层；实现缓存、来源和断网降级。验收：上海/伦敦/跨夏令时/极昼地区的当地时间与日界正确；断网仍有天色与作息。

**B. 睡眠与疾病。** 引入独立姿态及实际睡眠累计；按真实时间边界扩展离线结算；替换 30 分钟不互动即睡；接入病中休息。验收：跨午夜工作、叫醒、反复互动、病中午睡、药物治疗、两天离线与时钟回拨均能复现；同一输入可确定性重算。

**C. 面板与内容。** 设置页城市搜索/作息预览，主屏、状态页、悬浮猪、钓鱼、提示优先级和无障碍低动态模式联动。验收：面板开关、拖动、不同皮肤、窄屏、病猪睡眠与离线归来在真实浏览器检查；状态文字与画面一致。

**D. 数值校准与灰度。** 用固定种子跑健康日、低饱食夜、病中多次叫醒、长期离线、跨时区、雨天户外活动及天气缺失；指标至少包括每日需要照料次数、睡前/醒后数值、疾病恶化与自愈分布、外部接口请求次数。先通过既有 `npm run build`、`npm test`、`npm run typecheck`，再做真实浏览器和桌面宿主验收。数字不达目标时调参数，不通过增加隐藏惩罚补偿。

## 8. 需要在实现前锁定的产品决定

1. 城市默认采用“玩家手动选择”；设备定位仅作为主动点击的捷径。未选城市时先用设备时区显示时间，并显示“设置城市以同步当地天气与日出日落”。
2. 默认作息为规律型 21:30–07:00；三档同等计划睡眠长度。
3. 天气首版必须真实接入并贯穿展示；数值先仅受实际睡眠与照料影响。户外天气收益作为第二阶段，在已有室内/户外活动标记和离线规则后加入。
4. 天气供应商先按 Open-Meteo 的官方接口设计可替换适配器；上线方式须满足其非商业条款或改用获准方案，并显示数据来源。

## 9. 官方接口资料

## 10. 2026-10-03 资源与体验审查补充

以下为只读代码审查和隔离基准，未在用户真实 DSH/Electron 进程中采集 CPU 或内存。新昼夜与天气系统应先消除这些已有开销，再增加刷新源。

- 当前面板每 4 秒请求完整状态。新猪快照约 102 KB，其中图鉴、工作、商店等少变资料约占 95%；按连续打开计算，原始本地响应约 92 MB/小时。把静态目录按版本缓存，动态状态单独传输；天气应独立缓存，不能随四秒轮询访问外部服务。
- 每次 `freshen()` 都安排带 `fsync` 的存档写入，四秒轮询可形成约 900 次/小时写入。保持在线礼包规则的同时合并进度写盘，在跨奖励或重要动作时立即持久化。
- 每次快照都清空并重建整个面板内容。减少无变化重绘；输入、图鉴搜索、钓鱼 QTE 等正在操作的节点应保留焦点与会话。桌面外壳每 120 毫秒量一次布局，需要在真正变化和拖动时更新。
- 已复现离线日记归属错误：2026-10-02 20:00 开始 30 分钟搬砖，10 月 3 日中午再打开，10 月 2 日日记写“今天主人没来，我睡了一整天”，搬砖却计入 10 月 3 日。原因是 `store/api.js` 的 `freshen()` 先调用 `writeDiaryIfNewDay()`，后调用 `decay()` 结算历史活动。新增睡眠与天气日记前必须把事件按发生时刻归入正确的当地游戏日。
- 猪与道具存在常驻 CSS 动画，当前 `prefers-reduced-motion` 只覆盖部分图鉴和交互动画。昼夜天气粒子应有低动态模式、不可见时停更和数量上限。
